# Lifecycle: file_event_lnx_systemd_unit_creation

| Date       | Status       | Change                                         | Justification |
|------------|--------------|------------------------------------------------|---------------|
| 2024-03-16 | experimental | Rule authored with file_event log source       | Initial coverage, untested in production |

Promotion path: `experimental` → `test` after two weeks of shadow mode,
target < 5 FPs/day per 1,000 hosts. The primary FP source is **legitimate
administrator service creation** during app deployment — this is expected
to be high on fleets with active development (dev/staging), and lower on
production (where service creation is typically gated by change control).
The second FP source is **application installers** that ship .service files
via `make install` — these are not package-managed and are indistinguishable
from adversary writes at the file-event level; tune by allow-listing the
installer's exe path per fleet. → `stable` once the config-management and
installer filters are validated and FP rate is < 2/day. **Verification
step beyond FP rate:** confirm the fleet's file_event pipeline (Falco,
osquery, Wazuh, or auditd) actually emits events for the watched paths
— this rule was authored against a generic file_event schema and the field
names (`file.path`, `file.action`, `process.executable`) must be mapped
to the actual backend's schema during the test phase. If the fleet is
auditd-only, use the auditd variant documented in the hypothesis instead.

**Deployment note:** this rule is *not* a drop-in for auditd-only fleets.
The file_event log source assumes a modern file-integrity pipeline. If the
fleet standardizes on auditd, deploy the auditd variant (same detection
logic, different schema) rather than this rule. The two are functionally
equivalent but schema-incompatible; pick one per fleet and document which.
