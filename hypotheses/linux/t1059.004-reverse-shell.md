# Hypothesis: T1059.004 — Unix Shell Reverse Shell

## Statement
If an adversary achieves code execution on a Linux host (via a web app
RCE, a deserialization bug, a misconfigured service, or a stolen SSH key
used non-interactively), their first post-exploitation move is to establish
an interactive foothold — a reverse shell. The reverse shell connects
outbound to an attacker-controlled listener, bypassing inbound firewall
rules, and pipes a real terminal over the socket. It is the single most
common post-exploitation payload on Linux and the highest-signal
process_creation event in this corpus.

## Observable
A process_creation event where the command line matches one of:
  (a) bash/sh/dash/zsh/ksh with `/dev/tcp/` or `/dev/udp/` redirection
  (b) nc/ncat/netcat with `-e`, `-c`, `--exec`, or `--sh-exec`
  (c) socat with `EXEC:` or `SYSTEM:`
  (d) python/perl/ruby/php with socket-creation + spawn patterns
  (e) mkfifo against /tmp/, /dev/shm/, or /var/tmp/
Excludes Ansible/SSH parent processes, socat in LISTEN mode, and
netcat in listen mode (which are inbound, not outbound).

## Why process_creation, and why this rule is portable
Days 1–6 used auditd or file_event because the targets were file paths.
This rule is different: the reverse shell is a *command line*, and the
command line is available in every process-accounting pipeline —
auditd EXECVE, Sysmon for Linux, osquery process_events, Wazuh
process monitoring, Falco, and eBPF-based agents (Tetragon, Tracee).
That makes this rule the most portable in the series: it works on any
host with process accounting, regardless of whether the host has auditd
file watches or a file_event pipeline deployed. It is also the rule most
likely to fire *first* during an intrusion, because the reverse shell
precedes almost every other post-exploitation action.

## Telemetry prerequisite
Process creation with command line, via any of:
  - auditd EXECVE records (requires `-a always,exit -F arch=b64 -S execve`)
  - Sysmon for Linux (EventID 1)
  - osquery process_events table (requires es_process_events or bpf)
  - Wazuh process monitoring (whodata)
  - Falco `execve` / `spawned_process` rules
  - Tetragon / Tracee process_exec events

## Why it beats alerting on the network connection
Alerting on outbound connections (e.g., a new process opening a socket to
an external IP) is high-volume and low-signal — every `curl`, every package
update, every browser tab fires it. Alerting on the *command line pattern
that creates a reverse shell* is high-signal: the intersection of "spawns
a shell" + "pipes it to a socket" + "matches a known one-liner pattern" is
tiny in legitimate operations. The command line is also available *before*
the connection is established, so the alert fires at the earliest possible
moment.

## Known blind spots
- **Obfuscated one-liners** — an adversary who base64-encodes the payload
  (`echo <b64> | base64 -d | bash`) or splits it across multiple commands
  will not match the command-line patterns. Pair with a rule on
  `base64 -d | bash` (planned) and on encoded-command execution
  (analogous to Windows `-EncodedCommand`, T1059.004 sibling).
- **Statically-linked custom binaries** — an adversary who compiles their
  own reverse-shell binary and runs it will not match any interpreter
  pattern. The only signal is the outbound connection, which is a
  different rule (T1071 / T1095).
- **Compiled language one-liners** — `gcc -x c - <<< '<code>'` or
  `go run <file>` can build a reverse shell without matching any of the
  interpreter patterns. Rare in commodity attacks but common in
  targeted ones.
- **Named pipe relays where the relay binary is renamed** — `mkfifo`
  itself is matched, but a custom relay binary named `/usr/bin/foo`
  will not be. The mkfifo filter covers the common pattern; a custom
  relay requires behavioral detection (outbound connection from a
  shell-spawned process), which is out of scope for this rule.
- **Legitimate use** — red team exercises, CTF infrastructure, and
  developer connectivity tests all use these one-liners. Expect FP on
  dev/staging fleets; tune by destination IP and operator identity.

## Why "critical", not "high"
This is the only rule in the series rated `critical`. The reasoning:
  - A reverse shell *is* the intrusion. It is not a precursor (like a
    key write or a shadow read) — it is the moment the adversary gains
    interactive control of the host.
  - The signal is unambiguous: legitimate operations almost never spawn
    `bash -i >& /dev/tcp/...`, and the FP surface is narrow enough that
    a single firing warrants immediate human review.
  - The blast radius of a missed reverse shell is total host compromise;
    the cost of a false positive is a 10-minute triage by an analyst.
    The asymmetric cost justifies `critical` even at the price of some
    FP noise on dev fleets.
