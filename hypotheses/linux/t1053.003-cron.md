# Hypothesis: T1053.003 — Cron Job Creation / Modification

## Statement
If an adversary establishes persistence on a Linux host, cron is a preferred
mechanism because it survives reboots, needs no active session, executes as
the owning user (often root when placed in /etc/cron.d), and is rarely
audited for content changes.

## Observable
An auditd PATH record naming a cron file or spool directory, paired with a
SYSCALL record for open/openat/creat/rename/unlink; OR an EXECVE of
`crontab` with `-e`, `-r`, or `-i`. Excludes package-manager, config-
management, and systemd-cron writers.

## Telemetry prerequisite
auditd watch on cron paths, e.g.:
  -w /etc/crontab -p wa -k cron
  -w /etc/cron.d/ -p wa -k cron
  -w /etc/cron.hourly/ -p wa -k cron
  -w /etc/cron.daily/ -p wa -k cron
  -w /etc/cron.weekly/ -p wa -k cron
  -w /etc/cron.monthly/ -p wa -k cron
  -w /var/spool/cron/ -p wa -k cron
  -w /usr/bin/crontab -p x -k cron
On RHEL/CentOS, `/var/spool/cron/<user>`; on Debian/Ubuntu,
`/var/spool/cron/crontabs/<user>` — both are covered.

## Why it beats alerting on execution
Alerting on the *write* catches the persistence implant at install time,
before the first scheduled execution. That gives responders a chance to
isolate the host before the adversary's beacon fires.

## Known blind spots
- Hosts without auditd (eBPF-only) → does not fire. Pair with a Falco rule
  on `open_write` for the same paths.
- Writes performed through a privileged helper (e.g., a setuid wrapper that
  opens the file on behalf of an unprivileged caller) may attribute the
  writer to the helper rather than the attacker's process.
- Containerised cron (cron running inside a container with its own spool)
  only surfaces if the host audit subsystem covers container namespaces.
