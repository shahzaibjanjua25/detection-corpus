# Hypothesis: T1548.003 — Sudoers Modification

## Statement
If an adversary has write access to /etc/sudoers or /etc/sudoers.d/ (via
misconfiguration, a writable drop-in, or a compromised service running as
root), they will grant themselves NOPASSWD: ALL. This is preferred over
credential theft because it survives password rotation, avoids failed-login
alerts, and needs no interactive authentication.

## Observable
An auditd PATH record naming a sudoers path, paired with a SYSCALL record for
open/openat/creat/rename/chmod/unlink; excludes visudo invocations, package
managers, config-management tooling, and the sudo/sudoedit binaries
themselves.

## Telemetry prerequisite
auditd watch on sudoers paths, e.g.:
  -w /etc/sudoers -p wa -k sudoers
  -w /etc/sudoers.d/ -p wa -k sudoers
  -w /etc/sudo.conf -p wa -k sudoers
  -w /usr/sbin/visudo -p x -k sudoers
Note: `-p wa` covers write and attribute changes; add `d` if your auditd
version emits PATH records for unlink (needed to catch deletion of a
drop-in used to hide tracks).

## Why it beats alerting on sudo execution
Alerting on `sudo` execution is high-volume and low-signal (every admin
uses it). Alerting on the *policy write* catches the privilege-escalation
implant at install time, before the adversary's first NOPASSWD: ALL rule
is exercised. That gives responders a chance to isolate before the attacker
runs `sudo su -`.

## Known blind spots
- Hosts without auditd (eBPF-only) → does not fire. Pair with a Falco rule
  on `open_write` for the same paths.
- Writes performed through a privileged helper (e.g., a setuid wrapper that
  opens the file on behalf of an unprivileged caller) may attribute the
  writer to the helper rather than the attacker's process.
- Containerised sudo (sudo running inside a container with a bind-mounted
  sudoers) only surfaces if the host audit subsystem covers container
  namespaces.
- LDAP-backed sudoers (sudo-ldap / sssd) → no local file write; needs a
  separate rule on the directory-server side, out of scope here.
