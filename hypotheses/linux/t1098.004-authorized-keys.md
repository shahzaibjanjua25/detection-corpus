\# Hypothesis: T1098.004 — SSH Authorized Keys Modification



\## Statement

If an adversary gains any level of code execution on a Linux host, they will

prefer writing a public key into `\~/.ssh/authorized\_keys` over setting a

password, because it survives password rotation, avoids failed-login alerts,

and needs no interactive credential.



\## Observable

An `openat`/`write`/`rename\*` syscall against a path matching

`\*\*/.ssh/authorized\_keys\[2]`, emitted as auditd PATH + SYSCALL records,

where the writing process is not a sanctioned config-management binary.



\## Telemetry prerequisite

auditd watch on the file, or a recursive watch on `.ssh` directories, e.g.:

&#x20; -w /root/.ssh/ -p wa -k ssh\_keys

&#x20; -w /home/ -p wa -k ssh\_keys   (or per-user watches via a deployer)



\## Why it beats the alternative

Password changes are noisy and reversible; key insertion is silent and

persistent. This rule targets the \*write\*, not the later \*login\*, so it fires

at the moment of persistence rather than after the adversary is already in.



\## Known blind spots

\- eBPF-only hosts without auditd → rule will not fire. Pair with the Falco

&#x20; equivalent if that agent is deployed.

\- Writes performed through a pre-existing privileged process (e.g. sshd's

&#x20; own `AuthorizedKeysCommand`) will not surface as a distinct writer.
