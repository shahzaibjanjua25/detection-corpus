# Hypothesis: T1543.002 — Systemd Service Creation

## Statement
If an adversary establishes persistence on a modern Linux host, systemd
service units are the preferred mechanism on systemd-based distros
(RHEL 7+, Ubuntu 16.04+, Debian 8+, most container hosts). A .service unit
dropped into /etc/systemd/system/ gives the adversary: execution on every
boot, automatic restart on failure or crash, resource limits that avoid
suspicion, and journal logging that looks identical to legitimate services.
It is the natural successor to /etc/init.d/ scripts and the SysV runlevel
mechanism, and it is far harder to spot because the unit is a text file
that any admin can read — but few do.

## Observable
A file_event on a .service unit under /etc/systemd/system/, /etc/systemd/user/,
or ~/.config/systemd/user/, with an action of create/modify/rename/chmod,
where the writing process is not a package manager, config-management tool,
systemctl itself, or a known unit-installer helper.

## Why file_event, not auditd or process_creation
Days 1–5 all used auditd (or a process_creation branch) because the target
was a known file path and auditd watches are the natural fit. This rule is
different: unit files are created by *many* writers — editors (vi, nano,
systemctl edit), deployment scripts (tee, install, cp), package managers
(dpkg, rpm), and config-management tools (Ansible, Puppet). Auditing every
possible writer's process_creation is brittle; the file event itself is the
common denominator. This is also the first rule in the series where the
log source is `file_event` rather than `auditd` — it assumes the fleet has
a file-integrity or file-event pipeline (Falco, osquery file_events,
Wazuh syscheck, auditd -w on the paths), not necessarily auditd. If the
fleet has only auditd, this rule can be re-expressed as an auditd PATH
rule (see "auditd variant" below).

## Telemetry prerequisite
For a file_event pipeline:
  - Falco: rule on open_write/create for /etc/systemd/system/*.service
  - osquery: file_events table on /etc/systemd/system/%% (wildcard)
  - Wazuh: <directories check_all="yes">/etc/systemd/system</directories>
  - auditd (fallback): -w /etc/systemd/system/ -p wa -k systemd_unit

## auditd variant (if file_event unavailable)
  selection_path:
    type: 'PATH'
    name:
      - '/etc/systemd/system/*.service'
      - '/etc/systemd/user/*.service'
  selection_syscall:
    type: 'SYSCALL'
    syscall: ['openat', 'open', 'creat', 'rename', 'renameat', 'renameat2']
  condition: selection_path and selection_syscall and not <filters>
This loses the `chmod` detection (chmod is not a write syscall in all
kernels) and requires the same filter list. Prefer file_event where
available.

## Why it beats alerting on service start
Alerting on `systemctl start` is high-volume and low-signal — every
legitimate service start fires it. Alerting on the *unit file write*
catches the persistence implant at install time, before the adversary's
first boot-persisted execution. The difference matters: a responder who
sees the write can isolate before the next reboot; a responder who sees
the start is already looking at post-persistence activity.

## Known blind spots
- **Transient units** — `systemd-run --unit=foo` creates an in-memory
  unit via D-Bus without writing a file. This is the single biggest gap;
  a separate rule on `systemd-run` EXECVE is needed (planned).
- **Generators** — systemd generators (/usr/lib/systemd/system-generators/)
  can synthesize units at boot without writing to the watched paths.
  Rare in adversary tooling but worth noting.
- **Drop-in directory** — /etc/systemd/system/foo.service.d/*.conf files
  override existing unit behavior. This rule matches *.service only; a
  drop-in override that changes ExecStart is an equally valid persistence
  path and needs a separate rule (or extend the path list, with a
  corresponding FP increase because drop-ins are common for legitimate
  customization).
- **SysV init compatibility** — /etc/init.d/ scripts are still used on
  some distros and by some legacy software. T1543.002 covers systemd
  specifically; a separate T1037.004 (RC Scripts) rule is needed.
- **User units** — /home/*/.config/systemd/user/ units run as the user,
  not root. Lower privilege but still persistent; included in the rule
  because the path is unambiguous, but the severity of a user-unit
  implant is lower than a system-unit implant.
